Recorrido completo para la defensa: un usuario se registra y carga una comida

  1. App: en RegisterScreen se completa el formulario. validateRegister revisa los datos en el celular, antes de enviar nada.
  2. App: AuthContext.register llama a authApi.register, que usa publicApi, que a su vez usa rawRequest para hacer el fetch.
  3. API: Express recibe POST /api/auth/register. La petición pasa por authLimiter, que limita los intentos, y después por validate(registerSchema), que vuelve a validar los datos con zod.
  4. API: auth.service.register guarda el hash de la contraseña con bcrypt, crea al usuario como atleta y sendCode envía el código de 6 dígitos por email.
  5. App: se abre VerifyEmailScreen. El usuario escribe el código y se llama a verifyEmail.
  6. API: consumeCode comprueba el código (dentro de una transacción). Si es correcto, issueTokens crea el JWT de acceso y el refresh token.
  7. App: startSession guarda los tokens en SecureStore y despacha SIGN_IN. Al cambiar el estado, Stack.Protected muestra las pestañas del atleta.
  8. App: en DiaryEntryScreen el usuario busca "milanesa", la elige, carga 200 g y guarda.
  9. API: POST /api/diary pasa por authenticate, que valida el JWT y vuelve a leer al usuario de la base. Después createEntrySchema valida los datos y diary.service.createEntry calcula los macros en el servidor con scaleFood.
  10. App: al volver a la pestaña, useResource recarga el día y MacroSummary actualiza los anillos de calorías y macros.

Ideas clave para explicar

  • Validación en dos capas: la app valida para que el usuario reciba la respuesta al instante, y el servidor vuelve a validar con zod, porque es la única validación en la que se puede confiar. Las dos usan las mismas reglas.
  • Seguridad:
    • Las contraseñas se guardan con bcrypt.
    • Los tokens y los códigos se guardan como hash.
    • Las consultas SQL son parametrizadas, lo que evita la inyección SQL.
    • Hay límites de intentos.
    • El algoritmo del JWT está fijado.
    • Los refresh tokens se rotan y se detecta si uno se reutiliza.
    • El login social usa PKCE y no vincula cuentas automáticamente si el email no está verificado.
    • Las respuestas no revelan qué emails están registrados.
  • Roles:
    • En el servidor, authorize y resolveTargetUser controlan quién puede hacer qué.
    • En la app, Stack.Protected y Tabs.Protected muestran solo lo que corresponde a cada rol.
  • Patrón del backend: routes, después service y después MySQL. Los errores se convierten en un JSON uniforme en errorHandler.
  • Una sola app para todas las plataformas: Android, iOS y la web salen del mismo código. Algunos archivos tienen una versión .web.js que Expo usa automáticamente en el navegador.

config/db.js — conexión a MySQL

  • pool (5-12): un pool reutiliza conexiones en vez de abrir una por consulta.
    • ...env.db: host, puerto, usuario, clave, base y SSL salen del .env.
    • waitForConnections + connectionLimit: si están todas ocupadas, la consulta espera en fila.
    • dateStrings: true: las fechas llegan como texto AAAA-MM-DD (evita corrimientos de zona horaria).
    • decimalNumbers: true: los DECIMAL llegan como número, no como texto.
    • charset: 'utf8mb4': admite tildes, ñ y emojis.
  • (15) Cada conexión nueva fija la zona horaria de Argentina (−03:00).
  • query(sql, params) (18-21): ejecuta una consulta parametrizada (los ? se reemplazan de forma segura → evita inyección SQL) y devuelve solo las filas.
  • transaction(work) (24-37):
    1. Toma una conexión propia.
    2. beginTransaction().
    3. Ejecuta la función work(conn) con esa conexión.
    4. Si todo salió bien → commit() y devuelve el resultado.
    5. Si algo falló → rollback() (deshace todo) y relanza el error.
    6. finally → devuelve la conexión al pool.

middlewares/auth.js

authenticate(req, res, next) (8-32) — protege rutas

  1. Lee el encabezado Authorization y lo separa en esquema y token.
  2. Si no es Bearer <token> → 401 "Falta el token".
  3. jwt.verify comprueba la firma con el secreto y el algoritmo permitido.
    • Token vencido → 401 TOKEN_EXPIRED (la app usa ese código para renovar la sesión sola).
    • Firma inválida → 401 TOKEN_INVALID.
  4. Si el token no es de tipo access (por ejemplo, alguien manda un refresh) → inválido.
  5. Busca al usuario en la base en cada petición: así un cambio de rol o una baja se aplica al instante.
  6. Si no existe → 401; si está desactivado → 403.
  7. Guarda req.user = { id, role, coachId } y sigue (next()).

authorize(...roles) (35-40)

Función que devuelve un middleware. Si el rol del usuario no está en la lista → 403. Uso: authorize('admin').

middlewares/errorHandler.js

  • notFoundHandler: responde 404 con el método y la ruta pedida.
  • errorHandler(err, ...): traduce cualquier error a { error: { code, message, details } }:
    1. ZodError (validación) → 400 VALIDATION_ERROR con la lista campo + mensaje (la app lo muestra debajo de cada input).
    2. HttpError (errores propios) → su estado y código.
    3. JSON mal formado → 400; cuerpo muy grande → 413.
    4. ER_DUP_ENTRY (clave única de MySQL repetida) → 409.
    5. Base caída o mal configurada → 503.
    6. Cualquier otro → se registra en consola y se responde 500 sin detalles internos (no filtra información).

middlewares/validate.js — validate(schemas)

Recibe esquemas zod para params, query y body. Para cada parte presente ejecuta .parse(): si los datos no cumplen, zod lanza un error (lo atrapa el errorHandler); si cumplen, deja los datos limpios y convertidos (por ejemplo "5" → 5) en req.valid.

utils/access.js — resolveTargetUser(req, requestedUserId, { coachCan })

Decide sobre qué usuario actúa una petición tipo "ver el diario de X":

  1. Sin userId o con el propio id → actúa sobre uno mismo.
  2. Busca al usuario pedido; si no existe → 404.
  3. Admin → puede sobre cualquiera.
  4. Coach → solo si la ruta lo permite (coachCan), el objetivo es atleta y está asignado a ese coach.
  5. En cualquier otro caso → 403.

utils/dates.js

  • dateRange(from, to): lista de todas las fechas entre dos, inclusive (para gráficos por día).

utils/httpError.js

  • Atajos: badRequest (400), unauthorized (401), forbidden (403), notFound (404), conflict (409), badGateway (502, falló un servicio externo), unavailable (503).

  • mailConfigured(): true si hay host, usuario y clave SMTP.

    1. Si hay un emisor de prueba, lo usa.
    2. Sin SMTP: en producción tira 503; en desarrollo imprime el email (con el código) en la consola.
    3. Con SMTP: crea el transporte de nodemailer una sola vez (??=), con secure si el puerto es 465, y envía.

utils/validation.js — piezas de validación reutilizables (zod)

  • idParam: el :id de la URL convertido a entero positivo.
  • isoDate: formato AAAA-MM-DD y fecha real (rechaza 2025-02-30: al convertirla y volver a texto no da lo mismo).
  • pagination / paginationMeta: página ≥ 1, límite 1-100 (por defecto 20); calcula el total de páginas.
  • EMAIL_MAX = 190 (largo de la columna), PASSWORD_MAX = 72 (bcrypt ignora lo que pase de 72 bytes).
  • emailField: recorta espacios, pasa a minúsculas y después valida formato y largo.

auth.routes.js — las URLs de /api/auth

Limitadores de intentos (contra fuerza bruta):

  • authLimiter (17-23): máximo 50 peticiones cada 15 minutos por IP en registro, código, recuperación y OAuth. Cuando se supera, responde 429 TOO_MANY_REQUESTS.

/oauth/:provider/start, paso a paso:

  1. Lee el proveedor de la URL y, de la query, redirect_uri (a dónde volver) y code_challenge (PKCE).
  2. getProvider comprueba que el proveedor exista y esté configurado.
  3. assertAppRedirect solo deja volver a la propia app. Esto evita que un atacante use la API para mandar el código a su sitio.
  4. signState firma un "state" con el proveedor, la URI y el desafío.
  5. Redirige al usuario a la pantalla de inicio de sesión de Google, Facebook o GitHub.

/oauth/:provider/callback, paso a paso:

  1. Verifica la firma del state. Si alguien lo alteró o venció, responde error.
  2. Comprueba que el proveedor de la URL sea el mismo que quedó guardado en el state.
  3. Si el usuario canceló, o no llegó code, vuelve a la app con error=cancelled.
  4. fetchProfile canjea el code con el proveedor y obtiene el perfil (id, email y nombre).
  5. linkSocialAccount busca o crea al usuario.
  6. createLoginCode genera un código de un solo uso que vale 2 minutos.
  7. Redirige a la app con ese code.
  8. Si falla cualquier paso, redirige a la app con el error, porque el usuario está en el navegador y no vería un JSON.

auth.schemas.js — qué datos acepta cada ruta (zod)

z.object descarta las claves desconocidas. Por eso, aunque alguien mande "role": "admin" en el registro, ese dato nunca llega al service.

  • registerSchema: nombre, email de un dominio permitido y contraseña fuerte.
  • code: exactamente 6 dígitos (/^\d{6}$/), sin los espacios de los extremos.
  • verifyEmailSchema: email y código. resendCodeSchema: email y propósito (verify o reset; por defecto verify).
  • forgotPasswordSchema: email. resetPasswordSchema: email, código y contraseña nueva fuerte.
  • loginSchema: email y contraseña (sin pedir fortaleza).
  • refreshSchema y logoutSchema: el token, de hasta 2000 caracteres.
  • oauthParams: solo google, facebook o github.
  • oauthStartQuery: redirect_uri y un code_challenge que sea un SHA-256 en hexadecimal (64 caracteres).
  • oauthExchangeSchema: el código y un codeVerifier de 43 a 128 caracteres (lo que fija el estándar PKCE).
  • changePasswordSchema: la contraseña actual es opcional, porque una cuenta creada con red social no tiene; la nueva tiene que ser fuerte.

auth.service.js — la lógica

  • BCRYPT_ROUNDS = 10: costo del hash. Cada contraseña tarda unos milisegundos en procesarse, lo que encarece los ataques de fuerza bruta.
  • DUMMY_HASH: hash de relleno. Cuando el email no existe se compara igual contra él, así la respuesta tarda lo mismo y nadie puede deducir qué emails están registrados midiendo el tiempo.
  • findUserById(id): un SELECT con las columnas del usuario y el nombre del coach (USER_COLUMNS/USER_FROM salen de users.mapper.js).
  • session(row): si la cuenta está desactivada responde 403; si no, devuelve { user, tokens } con el usuario sin datos sensibles y un par de tokens nuevo.
  • findByEmail(email): busca al usuario por email.

register({ name, email, password })

  1. Busca si el email ya existe.
  2. Si existe y ya está verificado, o es una cuenta social, responde 409 "Ya existe una cuenta".
  3. Genera el hash de la contraseña. La contraseña nunca se guarda en texto plano.
  4. Si existía una cuenta sin verificar, le actualiza el nombre y el hash. Así, si alguien registró tu email antes, no te bloquea: quien recibe el código es el dueño del email.
  5. Si no existía, la inserta con el rol athlete, porque el registro público nunca crea coaches ni admins.
  6. Si está en producción y no hay correo configurado, marca la cuenta como verificada y devuelve la sesión directamente.
  7. Si no, manda el código y devuelve { verificationRequired: true, email }.

verifyEmail({ email, code })

  1. Busca la cuenta. Si no existe, responde el mismo error que con un código incorrecto, para no revelar qué emails existen.
  2. consumeCode comprueba el código.
  3. Marca email_verified_at. COALESCE conserva la fecha si ya tenía una.
  4. Devuelve la sesión.

resendCode({ email, purpose })

Si la cuenta no existe, está desactivada o (en el caso de verify) ya está verificada, no hace nada y responde igual. Si no, manda un código nuevo.

Con el propósito reset también se oculta el aviso "esperá un minuto" (CODE_RECENTLY_SENT): si no, al pedirlo dos veces seguidas se sabría qué emails tienen cuenta.

forgotPassword({ email })

Igual que el anterior, pero con el propósito reset. El error "ya te mandé un código hace menos de un minuto" se oculta, porque revelaría que la cuenta existe.

resetPassword({ email, code, newPassword })

  1. Busca la cuenta y consume el código.
  2. Guarda el nuevo hash y marca el email como verificado, porque recibir el código demuestra que el email es suyo.
  3. revokeAllForUser: cierra todas las sesiones abiertas (si alguien robó la cuenta, queda afuera).
  4. Devuelve una sesión nueva.

login({ email, password })

  1. Busca la cuenta por email.
  2. Si no existe: compara contra DUMMY_HASH, para gastar el mismo tiempo, y responde "Email o contraseña incorrectos".
  3. Si no tiene contraseña porque es social: avisa que entre con Google, Facebook o GitHub.
  4. Compara la contraseña con bcrypt.compare. Si no coincide, responde el mismo mensaje genérico.
  5. Si el email no está verificado: reenvía el código (ignorando el aviso de "hace menos de un minuto") y responde 403 EMAIL_NOT_VERIFIED. La app usa ese código de error para llevar al usuario a la pantalla del código.
  6. Si todo está bien, devuelve la sesión.

refresh(refreshToken)

consumeRefreshToken valida y revoca el token usado. Después busca al usuario y entrega una sesión nueva: es la rotación de tokens.

logout(refreshToken, { allDevices, userId })

Con allDevices, revoca todos los tokens del usuario; si no, solo el que recibió.

socialName(name)

Recorta el nombre a 100 caracteres sin partir emojis (Array.from separa por carácter real). Si queda vacío, usa "Usuario".

linkSocialAccount(provider, profile)

  1. Si el proveedor no mandó un id de usuario, responde 400.
  2. Normaliza el email (sin espacios y en minúsculas). Si es más largo de lo que entra en la columna, lo descarta.
  3. Llama a linkInTransaction.
  4. Si dos callbacks llegan a la vez, el segundo choca con la clave única (ER_DUP_ENTRY) y reintenta una sola vez.
  5. Si la cuenta está desactivada, responde 403. Si no, devuelve el id.

linkInTransaction(provider, profile) (dentro de una transacción)

  1. ¿Ya existe el vínculo proveedor + id en social_accounts? Entonces devuelve ese usuario.
  2. Si hay email, busca una cuenta con ese email:
    • Solo la vincula si el proveedor verificó el email y la cuenta es un atleta sin contraseña.
    • En cualquier otro caso responde 409: "Iniciá sesión con tu email y contraseña". Esto evita el robo de cuentas: alguien podría crear en Facebook una cuenta con un email ajeno sin verificarlo.
  3. Si no encontró ninguna cuenta, crea un atleta con el nombre, el email (verificado solo si el proveedor lo confirmó) y el avatar.
  4. Registra el vínculo en social_accounts y devuelve el id.

sessionForUser(userId)

Devuelve la sesión de un usuario por su id. Se usa en el canje del login social.

changePassword(userId, { currentPassword, newPassword })

  1. Busca el hash actual.
  2. Si la cuenta tiene contraseña, exige la actual y la compara. Si no coincide, responde 400.
  3. Si la nueva es igual a la actual, responde 400 SAME_PASSWORD.
  4. Guarda el hash nuevo y cierra todas las sesiones.

emailCodes.js — códigos de 6 dígitos por email

  • Constantes: el código vence a los 10 minutos, se invalida después de 5 intentos fallidos y hay que esperar 60 segundos para pedir otro.
  • hashCode(userId, purpose, code): SHA-256 de usuario:propósito:código. En la base se guarda solo ese hash: aunque alguien la robe, no puede leer los códigos.
  • MESSAGES: asunto y texto del email según sea para confirmar la cuenta o para cambiar la contraseña.

sendCode(user, purpose)

  1. Si se mandó un código hace menos de 60 segundos, responde 429 CODE_RECENTLY_SENT (anti-spam).
  2. Genera el código con crypto.randomInt, un azar criptográficamente seguro, y lo completa a 6 dígitos con ceros adelante.
  3. Borra el código anterior del mismo tipo, porque solo vale el último.
  4. Guarda el hash con un vencimiento de NOW() + 10 minutos.
  5. Manda el email en texto y en HTML. El nombre pasa por escapeHtml para que nadie pueda inyectar HTML en el email.

consumeCode(userId, purpose, code) (en una transacción)

  1. Lee el código con FOR UPDATE: bloquea la fila para que dos intentos simultáneos no se cuenten mal.
  2. Si no existe, venció o ya tuvo 5 intentos, el resultado es inválido.
  3. Si el hash no coincide, suma un intento y el resultado es inválido.
  4. Si coincide, borra el código (un solo uso) y el resultado es válido.
  5. Si el resultado fue inválido, responde 400 INVALID_CODE.

escapeHtml(value)

Reemplaza & < > " ' por sus entidades HTML.

oauth.js — piezas del login social (con PKCE)

PKCE (Proof Key for Code Exchange): la app inventa un secreto (el verifier) y le manda a la API solo su hash (el challenge). Al final, para canjear el código, tiene que presentar el secreto original. Si otra app intercepta el código, no le sirve sin ese secreto.

  • getProvider(name): devuelve el proveedor. Si no existe responde 400; si no está configurado, 501.
  • assertAppRedirect(uri, webOrigin):
    1. Si la URI no es válida, responde 400.
    2. Si es el mismo origen web que la API, la acepta: es la app web en el mismo dominio.
    3. Si no, el esquema tiene que estar permitido (macroentreno, y en desarrollo también exp/exps).
    4. Con macroentreno:// solo se permite el destino oauth-callback.
  • publicOrigin(req) / callbackUrl(req, provider): arman la URL pública de la API y del callback a partir de PUBLIC_API_URL, o del host de la petición en desarrollo.
  • signState(data): JWT de tipo oauth_state que vence en 10 minutos.
  • verifyState(state): verifica la firma y el tipo. Si falla, responde "La sesión de inicio expiró".
  • createLoginCode(userId, challenge):
    1. Limpia los códigos vencidos.
    2. Genera 32 bytes aleatorios en hexadecimal.
    3. Guarda el hash, el usuario, el challenge y un vencimiento de 120 segundos.
    4. Devuelve el código.
  • consumeLoginCode(code, codeVerifier) (en una transacción):
    1. Busca el código por su hash con FOR UPDATE.
    2. Lo borra siempre, aunque después falle la verificación: es de un solo uso.
    3. Si no existe, venció, o sha256(verifier) no coincide con el challenge, responde 401.
    4. Si todo está bien, devuelve el id del usuario.
  • appRedirect(appUri, params): agrega code o error como parámetros a la URI de la app.

socialProviders.js — Google, Facebook y GitHub

  • fetchJson(url, options): fetch con un tiempo límite de 10 segundos. Si no hay conexión, responde 502 PROVIDER_UNAVAILABLE. Devuelve { ok, body }.
  • providerError: 401 "Google (o el que sea) rechazó el inicio de sesión".

tokens.js — JWT de acceso y de renovación

  • JWT_ALGORITHMS = ['HS256']: fija el algoritmo. Se rechaza un token con otro algoritmo, incluso none, que es un ataque conocido.
  • signAccessToken(user): firma { sub: id, role, type: 'access' } con una vida de 15 minutos.
  • createRefreshToken(userId):
    1. Firma { sub, type: 'refresh', jti }. El jti es un UUID aleatorio, para que dos tokens nunca sean iguales.
    2. Calcula el vencimiento (30 días).
    3. Guarda en refresh_tokens el hash del token, no el token.
    4. Lo devuelve.
  • issueTokens(user): arma { accessToken, refreshToken, tokenType: 'Bearer', expiresIn }.
  • consumeRefreshToken(token) (la rotación):
    1. Verifica la firma y que el tipo sea refresh.
    2. Busca el hash en la base. Si no existe, el token es desconocido.
    3. Si ya estaba revocado, alguien está reusando un token viejo, posiblemente robado: se cierran todas las sesiones del usuario y se responde REFRESH_REUSED.
    4. Si no, lo marca como revocado y devuelve el id del usuario (después se emite un par nuevo).
  • revokeRefreshToken(token): revoca un token.
  • revokeAllForUser(userId): revoca todos los tokens del usuario.

Datos corporales (modules/body)

energy.js — el cálculo nutricional (funciones puras: no tocan la base)

  • ACTIVITY: factores de actividad, de 1,2 (sedentario) a 1,9 (muy activo), con sus textos para el formulario.
  • GOALS: objetivos posibles:
    • déficit: −0,5 / −0,75 / −1 % del peso por semana, con 2,2 g de proteína por kg;
    • recomposición: 95 % del gasto;
    • mantenimiento: 100 %, con 1,8 g de proteína por kg;
    • volumen: +0,25 / +0,35 / +0,5 % del peso por semana.
  • KCAL_PER_KG = 7700: la energía aproximada de 1 kg de tejido corporal.
  • round(n, step): redondea a 1, 10, 0,1 o 0,05 sin los errores de coma flotante (toFixed).
  • ageFrom(birthDate, today): resta los años y le quita 1 si este año todavía no cumplió.
  • energyPlan(p), paso a paso:

    1. Calcula la edad, la altura en metros y el IMC = peso / altura².

    2. Si se cargó el % de grasa, calcula la masa magra = peso × (1 − %grasa).

    3. Metabolismo basal (BMR):

      • con masa magra usa Katch-McArdle: 370 + 21,6 × masa magra;
      • sin masa magra usa Mifflin-St Jeor: 10·peso + 6,25·altura − 5·edad, más 5 en hombres o menos 161 en mujeres.

    4. Gasto total (TDEE) = BMR × factor de actividad.

    5. Calorías objetivo:

      • si el objetivo tiene ritmo: TDEE + (%semanal × peso × 7700 / 7), es decir, el cambio de peso semanal pasado a kcal por día;
      • si no tiene ritmo: TDEE × factor (0,95 o 1).

    6. Límites de seguridad:

      • nunca más del 25 % de déficit;
      • nunca por debajo del basal;
      • nunca más del 20 % por encima del gasto.

      Cada vez que se aplica un límite, se agrega una nota que lo explica.

    7. Peso de referencia para la proteína: con masa magra, masa magra / 0,85 sin pasar del peso real (Math.min); con obesidad (IMC ≥ 30), el peso que correspondería a un IMC de 25; en los demás casos, el peso real.

    8. Proteína = g/kg del objetivo (+0,2 g si es un déficit rápido) × peso de referencia.

    9. Grasa: entre el 25 % y el 35 % de las kcal, y como mínimo 0,8 g/kg.

    10. Carbohidratos = (kcal − proteína·4 − grasa·9) / 4. Son lo que queda.

    11. Avisos: IMC bajo con déficit, menor de 18 años, IMC ≥ 30 sin % de grasa.

    12. Devuelve la edad, el IMC y su categoría, el método usado, el BMR, el TDEE, el cambio semanal en kg (calculado con las kcal finales, después de los límites de seguridad: (kcal − TDEE) · 7 / 7700), las metas, la proteína por kg, el agua (35 ml/kg) y la fibra (14 g cada 1000 kcal).

  1. Tiene cuatro estados: data, error, loading y refreshing.

  • meal: la comida elegida.
  • mode: de dónde se toma el alimento: catalog, off, usda, fatsecret, manual o photo.
  • search y results: lo que se busca y lo que se encontró.
  • food: el alimento elegido.
  • form: los gramos, o los macros si es carga manual.
  • original: los valores originales cuando se edita, para saber qué cambió.

Efectos

  1. Edición (cuando llega un id):
    1. Carga el día y busca el registro. Si no existe, muestra un error.
    2. Pone la pantalla en modo manual y completa el formulario.
    3. Guarda una copia en original.
  2. Búsqueda en el catálogo, con debounce: espera 300 ms después de la última tecla para buscar, así no hace una petición por cada letra. Si el texto cambia antes, cancela el temporizador.
  3. Búsqueda en FatSecret: pide al menos 2 letras y espera 500 ms, porque es un servicio externo.

Funciones

  • searchExternal(): Open Food Facts y USDA buscan solo al tocar "Buscar", para respetar los límites de uso de esas bases.
  • pickExternal(item) / pickFatSecret(item): importan el alimento al catálogo, lo dejan elegido y completan los gramos con la porción del envase o con 100. Mientras importa, la fila muestra una ruedita.
  • changeMode(next): limpia los resultados y el alimento elegido, y cambia de modo.
  • NUMERIC + set(key): cada campo numérico pasa por el filtro decimal(), que no deja tipear letras ni un segundo decimal. Al escribir, se borra el error de ese campo.
  • visible: en FatSecret, con menos de 2 letras, no se muestran resultados viejos.
  • searchable: verdadero cuando se está eligiendo un alimento, es decir, no es carga manual ni foto.
  • preview (useMemo): las kcal y los macros calculados para los gramos escritos. Solo se recalculan cuando cambian el alimento o los gramos.
  • save():
    1. Si se eligió un alimento:
      • exige que haya uno elegido;
      • valida los gramos (mayores a 0 y hasta 5000);
      • manda solo foodId + grams, porque los macros los calcula el servidor.
    2. Si es carga manual:
      • valida los números: los gramos y las kcal son obligatorios; los máximos son 5000 g y 10000 kcal;
      • si los números están bien, controla la coherencia entre los macros y las calorías (validateMacroConsistency). Excepción: al editar un registro que viene del catálogo no se controla, porque si solo cambiaste los gramos el servidor recalcula los macros;
      • valida el nombre (de 2 a 150 caracteres);
      • si hay errores, los muestra y no envía nada.
    3. Si se está editando: manda solo lo que cambió. Si cambiaron únicamente los gramos, el servidor recalcula los macros.
    4. Llama a create o update y vuelve atrás. Si el servidor responde con errores, los muestra debajo de cada campo.
  • remove(): pide confirmación, borra el registro y vuelve.

  • text e image: lo que se está por enviar.
  • busy: 'thinking' (esperando la respuesta) o 'transcribing' (pasando el audio a texto).
  • failure: el último mensaje que no se pudo enviar.
  • speakAll: si todas las respuestas se leen en voz alta.

Efectos

  • Al salir de la pantalla, corta el audio.
  • Si la respuesta tarda más de 15 segundos, marca slow.

ask(history, { spoken })

  1. Manda los últimos 16 mensajes a aiApi.chat.
  2. Agrega la respuesta a la conversación, junto con sus actions.
  3. Si el usuario habló, o si está activado "leer todo", pide el audio de la respuesta y lo reproduce.
  4. Si hay un error:
    • De configuración o de validación: saca el mensaje de la conversación y lo devuelve al campo de texto, así no se pierde lo escrito.
    • Cualquier otro: marca el mensaje como fallido y muestra el botón "Reintentar".

El resto de las funciones

  • send(content): recorta el texto, arma el mensaje del usuario (con la foto, si hay), reemplaza cualquier mensaje fallido, vacía el campo y llama a ask.
  • retry(): quita la marca de fallido y vuelve a preguntar.
  • clearChat(): pide confirmación y borra la conversación. Lo que el asistente ya registró queda guardado.
  • toggleMic():
    1. Si no está grabando, empieza a grabar.
    2. Si está grabando, para la grabación y la manda a aiApi.transcribe.
    3. Si entendió algo, lo envía como un mensaje hablado; si no, avisa "No te escuché bien".
  • attach(source): elige una foto con pickImage y la deja lista para mandar.

Qué se dibuja

  • Encabezado: los botones de borrar la conversación y de leer en voz alta.
  • Lista de mensajes:
    • si la IA no está configurada, muestra AssistantSetup;
    • si no hay mensajes, muestra las sugerencias;
    • si hay, muestra las burbujas: verdes las del usuario y grises las del asistente.
  • Acciones del asistente: debajo de cada respuesta aparecen enlaces, por ejemplo "2 comidas registradas en cena", que llevan al diario o a los entrenos. Solo se muestran al atleta, que es quien tiene esas pestañas.
  • Indicador de espera: "Pensando…", "Escuchando lo que dijiste…" o "Sigo trabajando…".
  • Barra de escritura:
    • botones de cámara y galería;
    • el campo de texto, que se puede agrandar;
    • un botón enviar, si hay texto; si no, un botón de micrófono, que se pone rojo mientras graba;
    • un contador de caracteres que aparece cerca del límite.

Entrenador con cámara (features/coach/, solo en la web)

Funciona en el navegador con MediaPipe Pose, un modelo de Google que encuentra 33 puntos del cuerpo en cada cuadro del video. Todo el análisis se hace en el dispositivo: el video no se envía a ningún servidor.

Flujo general

  1. Preparación (SessionSetup): se elige cuántas series, el objetivo y el descanso. Se ve un maniquí 3D haciendo el ejercicio.
  2. En vivo (CoachSession.web.jsx):
    1. la cámara toma un cuadro;
    2. MediaPipe devuelve los puntos del cuerpo;
    3. se suavizan;
    4. el tracker cuenta las repeticiones y detecta los errores;
    5. el narrador decide qué decir;
    6. se dibuja el esqueleto sobre el video.
  3. Resumen (SessionSummary): las series, la calidad de la técnica y el error más frecuente. Ofrece guardar la sesión o devolver las series al formulario que abrió la cámara.

pose/engine.js — createTracker(rule): cómo cuenta las repeticiones

No usa ni la cámara ni la pantalla. Recibe poses y devuelve un estado: reps, badReps, holdMs, progress, message, failing, etc.

Constantes que lo hacen robusto:

Constante Para qué sirve
ARM_MS = 1000 Hay que estar 1 segundo quieto en la posición de inicio antes de que empiece a contar, así sentarse o acercarse caminando no cuenta como repetición.
MIN_REP_MS = 600 Un movimiento más rápido que esto es ruido, no una repetición.
MAX_JUMP = 55° Si el ángulo salta más que eso en un cuadro, es un error de detección y se ignora.
LOST_GRACE_MS = 600 Si una mano tapa la rodilla un momento, no se pierde la repetición.
SMOOTHING = 5 Se usa la mediana de los últimos 5 ángulos.
lockSide Siempre juzga el mismo lado del cuerpo; solo cambia si el otro se ve claramente mejor durante 400 ms.

update(lm, now), paso a paso:

  1. Comprueba que se vean los puntos que necesita la regla. Si no, explica qué hacer (lose).
  2. Calcula qué checks fallan y qué articulaciones pintar de rojo.
  3. Ejercicios que se sostienen (hold):
    • si la postura está mal, el reloj se detiene y se muestra la corrección;
    • si está bien durante 0,8 s, empieza a sumar tiempo.
  4. Ejercicios de repeticiones (reps):
    1. Calcula el ángulo y descarta los saltos.
    2. Calcula el avance: progress = (rest − ángulo) / (rest − peak), entre 0 y 1.
    3. Si todavía no arrancó, espera la posición de inicio durante 1 segundo y muestra "¡Listo! Arrancá".
    4. Cuando el avance pasa de 0,25, empezó una repetición: guarda el punto más profundo al que llegó y los errores de técnica.
    5. Cuando vuelve por debajo de 0,1, terminó la repetición:
      • si llegó al fondo (avance ≥ 1) y no tuvo errores durante 3 cuadros o más, cuenta: "¡Bien! Van N";
      • si llegó al fondo pero con mala técnica, no cuenta y muestra la corrección;
      • si llegó solo a la mitad (avance ≥ 0,35), no cuenta: "Bajá más…".
  5. isSetDone: la serie termina al llegar al objetivo de repeticiones o de segundos.

CoachSession.web.jsx — la pantalla en vivo

  • Fases: setup, starting, live, done o error. Para los errores (sin permiso, sin cámara, sin HTTPS, o el modelo no cargó) muestra un mensaje claro (PROBLEMS).
  • start():
    1. Comprueba que la página sea HTTPS y que haya cámara.
    2. Pide la cámara (getUserMedia, 1280×720).
    3. Carga MediaPipe.
    4. Crea el tracker y el narrador, y pasa a live.
  • loop(), que corre en cada cuadro:
    1. Detecta la pose y la suaviza.
    2. Mide los cuadros por segundo. Si durante 3 segundos analiza menos de 14 cuadros por segundo, cambia al modelo lite sin cortar la sesión.
    3. Si está en el descanso, cuenta el tiempo y después anuncia la serie siguiente.
    4. Si no, actualiza el tracker, le pregunta al narrador qué decir, dibuja el esqueleto y muestra "+1" o "No contó".
    5. Para no hacerlo más lento, actualiza la pantalla de React como máximo cada 100 ms.
    6. Cuando la serie termina, llama a completeSet.
  • completeSet(): guarda la serie. Si era la última, llama a finish(); si no, anuncia el fin de la serie y empieza el descanso.
  • finish(): guarda también una serie que quedó a la mitad, si se hizo algo. Apaga la cámara, pasa al resumen y lo dice en voz alta.
  • Otras funciones: activar y desactivar la voz (se recuerda la preferencia), la pantalla completa, la pausa y los datos de depuración (?debug) para calibrar los ángulos.
  • Al terminar:
    • si la cámara la abrió el formulario de una sesión, resolveCoach le devuelve las series y vuelve atrás;
    • si no, ofrece guardarla como una sesión nueva en Entrenos.
